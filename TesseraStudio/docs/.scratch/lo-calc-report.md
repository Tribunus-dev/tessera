## 3. Formula engine gap analysis

LO's formula engine has five architectural primitives that the Swift `FormulaEngine/` either lacks or has only a thin form of:

1. **RPN token array + opcode switch.** `compiler.cxx` (line 82-100, 7400 lines total) lexes source and emits a `ScTokenArray` of `FormulaToken` subclasses (line 22-25 of `compiler.hxx`) where each token is an `OpCode` (e.g. `ocAdd`, `ocIf`, `ocRange`, `ocMatRef`) plus a `StackVar` (`svSingleRef`, `svDoubleRef`, `svMatrix`, `svExternal`, ...). The interpreter (`interpr1.cxx` line 106-110 + ~36500 more lines across files 1-8: interpr1=14500, interpr2=3713, interpr3=6033, interpr4=4695, interpr5=3949, interpr6=1063, interpr7=557, interpr8=2008) is a giant `switch(OpCode)`. (Corrected from an original "14000" - that figure looks like it counted interpr1.cxx alone, not the full 1-8 set.) Tessera's `Evaluator.swift` is a **recursive AST walker** - semantically equivalent for scalar formulas but the Swift model has no way to emit an intermediate token array, so shared-formula optimization, jump-threaded CSE arrays, and the `ScJumpMatrix` control-flow pattern are not available. **Action:** keep the AST (it is the right design for Swift), but add a `TokenArray` IR alongside it so shared-formula cells and CSE arrays can share one compiled form. `TokenArray` should live in `FormulaEngine/TokenArray.swift` and be the canonical IR for `DependencyGraph`.

2. **Shared formula groups + invariant tracking.** `ScFormulaCellGroup` (`formulacell.hxx:71-102`) is the LO equivalent of Excel's "shared formula" - N consecutive cells that share one `ScTokenArray` but parameterize the relative references per row/column. It carries `mbInvariant`, `mbSubTotal`, `mbPartOfCycle`, and a calc state. Tessera's `SheetWorkbook.hydrate(from:)` (`SheetWorkbook.swift:54-85`) compiles every cell's formula independently - copying the AST per cell even when 100 cells are `=A1+ROW()`. **Action:** add `FormulaGroup { tokens: TokenArray, length: Int, parameterizedRefSlots: [RefSlot: Int] }` keyed on the group's top cell; `Evaluator` should look up the group on `FormulaAST.cell` and shift `refSlots[paramRow]`.

3. **Recalc state machine + cycle detection at the cell level.** LO's `ScFormulaCell` carries `meCalcState` per cell and `mbPartOfCycle` per group (`formulacell.hxx:86-87`). The `ScColumn` broadcast model (`column.cxx`, `brdcst.hxx`, `grouparealistener.hxx`) is a fan-out notifier: changing a cell marks its dependents dirty in a single pass. Tessera's `DependencyGraph.swift` has the bidirectional graph but no cell-level state - every `recalculate` re-walks the whole dependent cone. **Action:** evolve `DependencyGraph` to expose a `recalcPlan(after: CellAddr) -> [CellAddr]` (a topological order limited to the dirty cone) and a `markDirty(_: CellAddr)` that pushes onto a per-cell state enum; the cell itself should hold the cached `Value` so re-recalc on no-op edits is free.

4. **Name resolution in the compiler, not the evaluator.** `compiler.cxx` line 53-58 imports `rangenam.hxx`, `dbdata.hxx`, `addincol.hxx` - the compiler resolves `$MyRange` to a `DoubleRef` token at parse time, not at eval time. Tessera defers name resolution to `Evaluator.swift:70` (`engine.resolveNamedRange(name, at:)`), which means a renamed range silently re-resolves per call. **Action:** move name resolution into the `Parser` so the AST carries either a resolved `cell/range` node or an unresolved `name(string)` node with a "resolve at recalc" escape hatch.

5. **Volatile functions + array formula context.** Tessera's `FunctionVolatility` (`.notVolatile`/`.volatile`) covers NOW/TODAY/RAND/OFFSET/INDIRECT/INFO (`FunctionRegistry.swift:14`), but there is no `array` volatility tag. LO's `ScMatrixMode` (`formulacell.hxx:115-119` = `NONE`/`Formula`/`Reference`) lets a cell be the top-left of a CSE array, and the interpreter's `ScIfJump()` (`interpr1.cxx:106-110`) calls `MatrixJumpConditionToMatrix()` to broadcast a single-cell result across the array's range. **Action:** add `FunctionVolatility.array` to `FunctionRegistry` and a `FormulaAST.array(range: Range, head: FormulaAST)` form so FILTER, SORT, UNIQUE can be implemented.

**Function categories not yet registered:** `ID_FUNCTION_GRP_DATABASE` (1 - DSUM, DGET, DAVERAGE, DCOUNT, DMAX, DMIN, DPRODUCT, DSTDEV, DSTDEVP, DVAR, DVARP, DCOUNTA, GETPIVOTDATA), `ID_FUNCTION_GRP_INFO` (4 - CELL, ERROR.TYPE, INFO, ISBLANK, ISERR, ISERROR, ISEVEN, ISFORMULA, ISLOGICAL, ISNA, ISNONTEXT, ISNUMBER, ISODD, ISREF, ISTEXT, N, NA, TYPE), `ID_FUNCTION_GRP_MATRIX` (7 - MDETERM, MINVERSE, MMULT, MUNIT, SUMPRODUCT, TRANSPOSE), the rest of `ID_FUNCTION_GRP_MATH` (SUMIF, SUMIFS, COUNTIFS, AVERAGEIFS, MAXIFS, MINIFS, AGGREGATE, SUBTOTAL, SUMSQ, PRODUCT - partially there), and the `scaddins` surface (BESSELI/J/K/Y, ERF, ERFC, COMPLEX, IMABS, IMAGINARY, IMREAL, IMSUM, IMPRODUCT, IMSUB, IMDIV, CONVERT, DELTA, GESTEP, HEX2BIN, HEX2DEC, HEX2OCT, OCT2HEX, etc.). The `scaddins/source/analysis/` and `scaddins/source/datefunc/` addins are also part of the public function table; Tessera has a `DateFunctions.swift` and `StatisticsFunctions.swift` but no `AnalysisFunctions.swift` or `BesselFunctions.swift`.

**`DependencyGraph.swift` vs LO's `grouparealistener`:** Tessera's graph stores `cell -> precedents`, `cell -> dependents`, a `volatileCells` set, and `formulaASTs: [CellAddr: FormulaAST]` (all four at `DependencyGraph.swift:28-34`; an earlier draft of this line omitted the fourth). LO does not store the graph - it stores area listeners per formula-group (`formulacell.hxx:69 AreaListenersType`), and re-computes dependency by walking the `ScTokenArray` on every change. The Swift approach is **better for correctness, worse for performance**; the LO approach is **better for performance, worse for cycle detection**. The right evolution is: keep Tessera's explicit graph, but add a `FormulaGroup.areaListener` optimization for the contiguous-row case so 100 `=A1+ROW()` cells share one edge rather than 100.

## 4. SheetWorkbook vs ScDocument gap analysis

`ScDocument` is a `sc/inc/document.hxx` `3000+` line class that holds: (a) per-table `ScTable` arrays (data + draw layer + chart list), (b) a workbook-wide `ScRangeName` container (`sc/inc/rangenam.hxx`), (c) a `ScDBCollection` (database ranges, `sc/inc/dbdata.hxx`), (d) a `ScDPCollection` (pivots, `sc/inc/dpobject.hxx`), (e) a `ScValidationDataList`, (f) a `ScStyleSheetPool` (named styles, `sc/inc/stlsheet.hxx`), (g) a `ScConsolidationData` (consolidation), (h) a `ScChangeTrack` (`chgtrack.cxx`), (i) per-table `ScSheetProtection`, (j) a `ScLinkedArea` list (DDE/external links, `sc/inc/arealink.hxx`), (k) a `sc::SharedStringPool` (`sc/inc/sharedstringpoolpurge.hxx`), and (l) a `sc::FormulaGroupAggregator`. Tessera's `SheetWorkbook` (`SheetWorkbook.swift:27-50`) currently carries just `engine: SheetEngine` and `sheetID: UUID?`.

The deltas in priority order:

1. **Multi-sheet identity + sheet list** - `SheetWorkbook` must grow `sheets: [SheetID: SheetSnapshot]` where each `SheetSnapshot` references a `Sheet` document and an optional `SheetEngineState` (the engine lives on the workbook to share recalc). The current model hides the list inside `body: DocumentAST` of a single `Sheet`.
2. **Workbook-level named ranges** - `ScRangeName` keyed on `(name, scope)` with `scope = .workbook | .sheet(n)`. Tessera's `engine.resolveNamedRange` (`Evaluator.swift:70`) is workbook-scoped only and not persisted to the `Sheet` body.
3. **Database range list + pivot list** - `ScDBCollection` and `ScDPCollection` are per-document in LO; in Tessera they should hang off the `SheetWorkbook` so they can be imported/exported as a single `body` extension.
4. **Validation + conditional formatting registries** - per-range rules that survive across the `body` round-trip. Today they would have to live on each `Sheet` (one sheet at a time) which is wrong for cross-sheet rules.
5. **Shared-formula + change-track layer** - the `ScFormulaCellGroup` aggregation and the `ScChangeTrack` both need a workbook home, not a per-sheet home, because they reference cells across sheets. The receipt backbone can host the change track; the shared-formula group cache needs a new `FormulaGroupRegistry`.
6. **Number-format pool + style pool** - `sc/inc/zforlist.hxx` (`SvNumberFormatter`) and `sc/inc/stlsheet.hxx` are workbook-wide. Tessera's `Sheets/Sheet.swift:9-14` only has `SheetColumnType`, not a per-cell format index.

## 5. Chart / pivot / advanced features

- **Charts** - **best as a tesseracore component** evolving `BlockType` (which already has `table` and `tableCell` per the context block) to add a `.chart(ChartSpec)` case. Embedding an LO chart object via UNO is possible through `tessera_lo_service.py`, but the SwiftUI render path is the priority and LO chart objects don't render into a `SwiftUI.View`. A Swift-native `ChartRenderer` reading `ChartSpec` JSON is the right surface. **P1**.
- **Pivot tables** - **build a `PivotTableStore` in Swift**. UNO pivots return `ScDPObject` whose schema is not stable across versions; reusing it locks the codebase to LO's pivot model. The Swift model can be simpler (no `DataPilotFieldOrientation` matrix, just row/column/data/filter bins) and the calculation can be a single pass over the source range, paralleling how `ScDPTableData` works. **P2**.
- **Scenarios** - **punt to P2**. The scenario pane in `sc/source/ui/miscdlgs/scenwnd.cxx` is a Navigator tab that branches the worksheet to alternate sets of input cells; it is rarely used in the modern spreadsheet market and would not survive the receipt backbone model cleanly.
- **Solver** - **best as a UNO call** through `tessera_lo_service.py` exposing `com.sun.star.sheet.Solver` (`optsolver.cxx` line 49). The native LP/nonlinear implementation in LO is large (`solverutil.cxx` 1000+ lines) and ports would diverge. A `Solver` enum on `Sheet` that calls into the bridge is the right answer. **P2**.
- **Data validation** - **best as a Swift primitive**. UNO `XSheetCondition2` is awkward and validation rules are needed for the agent tool surface. Extend `Sheet` with `validation: [CellRange: ValidationRule]`. **P1**.
- **Conditional formatting** - **best as a Swift primitive**. Same rationale. Extend `Sheet` with `conditionalFormats: [CFEntry]`. **P1**.

## 6. Existing LibreOffice bridge surface - what to reuse

The bridge stack - `LibreOfficeBootstrap.swift` (discovers LO at `/Applications/LibreOffice.app` or bundled), `EmbeddedPythonBridge.swift` (CPython lifecycle), and `tessera_lo_service.py` (in-process UNO via `URE_BOOTSTRAP=libuuresolverlo.dylib`) - is already a working UNO gateway. Capabilities to reuse vs re-implement:

- **Importer for XLS, ODS, and legacy BIFF.** `sc/source/filter/excel/xetable.cxx`, `sc/source/filter/oox/excelhandlers.cxx`, and `sc/source/filter/xml/xmlimprt.cxx` collectively are 50+ years of accumulated edge-case handling. The right path is `loadDocument -> iterate ScDocument -> emit Tessera sheet JSON` inside `tessera_lo_service.py`, called through `EmbeddedPythonBridge.call(...)`. Re-implementing in Swift would be 20K+ LoC for marginal gain.
- **Solver, ODFF number-format, locale-aware DATE/NUMBER parsing.** All three have UNO interfaces (`Solver`, `XNumberFormatType`, locale services) and the Swift equivalents would be partial. Call UNO.
- **Print / page setup / headers/footers.** The `XMLTableHeaderFooterContext` and `pagesettings.cxx` round-trip code is best called through UNO when the user is exporting a sheet to PDF, but the stored representation in the `Sheet.body` JSON should be Swift-native. Read via UNO, store natively.
- **Pivot table rendering.** Call UNO for the `ScDPObject` if the user wants to embed an LO pivot in a chart, but for Tessera's own SwiftUI `PivotLayoutView`, the Swift model is correct.
- **Re-implement in Swift: formula engine, validation, conditional formatting, cell styles, number-format pool, sort/filter, named ranges, sheet protection, comments/notes.** These are the load-bearing primitives the receipts layer and the agent tool surface need direct access to; going through UNO for every read/write would be too slow and would not compose with the existing `SheetEngine` / `DependencyGraph` / `ReceiptsCoordinator` stack.

## 7. Proposed tesseracore component design (top 5)

1. **`TesseraCore/FormulaEngine/RecalcScheduler.swift`** - extends `DependencyGraph` rather than adding a parallel one. Inputs: `SheetEngine`, `CellAddr` of the edited cell, the new value. Output: a `RecalcPlan` = ordered `[CellAddr]` (topo-sorted within the dirty cone) plus a per-cell `RecalcState { dirty, scheduled, computing, done }` map. Reads from `DependencyGraph` (precedents/dependents) and from `SheetStore` (cell value lookups). The plan is consumed by `SheetWorkbook.recalculate(after:)` which already exists in spirit. Evolves the existing `SheetEngine` rather than adding a v2. Test: a sheet with 100 cells where cell A1 is a constant and B1..B100 = `A1*ROW()`; edit A1 from 1 to 2; assert the plan length is 100 and B100=200, not 100 recalculations on no-op data.

2. **`TesseraCore/Productivity/Materials/Sheets/SheetWorkbook.swift`** (evolution in place, not a new v2) - add `sheets: [SheetID: SheetSnapshot]`, `namedRanges: NamedRangeRegistry`, `validations: [RangeID: ValidationRule]`, `conditionalFormats: [RangeID: CFEntry]`, `pivots: [PivotID: PivotDescriptor]`, `protection: SheetProtection`. Inputs from `Sheet` documents on load, from the agent tool surface on edit. Output is consumed by `DocumentExporter` and the receipt pipeline. Test: a workbook with two sheets sharing a named range `MyTotal`; reference `MyTotal` from a third sheet; assert resolution and export round-trip.

3. **`TesseraCore/Productivity/Materials/Sheets/QueryEngine.swift`** - new component for sort/filter/subtotal. Inputs: a `Sheet`, a `QueryParam` (sort keys, filter criteria, subtotal descriptors), the `DependencyGraph` (to mark dirty cells after a sort). Outputs: a filtered/sorted `SheetsViewModel` snapshot plus dirty-cell invalidations forwarded to `ReceiptsCoordinator`. Evolves the same `SheetsViewModel` rather than adding a parallel model. Test: filter `Sheet` for `column A > 10`; assert dependents of the filtered rows are invalidated.

4. **`TesseraCore/Views/Renderers/ChartRenderer.swift`** - new component that consumes a `ChartSpec` JSON (type, data range, axes, title). Inputs: a `ChartSpec` carried in a `BlockType.chart(ChartSpec)`. Outputs: a `SwiftUI.View` rendered with Swift Charts. Not a UNO call; the data range resolves to cells via `SheetWorkbook` at render time. Test: a bar chart over `A1:B5`; assert it redraws when B2 changes (via the dependency graph's subscriber).

5. **`TesseraCore/Productivity/Materials/Sheets/CellFormat.swift`** (in-place evolution of `SheetColumn`) - extend the column type with `numberFormat: String?` (Excel format codes), per-cell `font`, `fill`, `border`, `alignment`. Inputs: a `CellAddr` and a `CellFormat`. Outputs: a `Value` view-model for SwiftUI that knows the display string. Evolves `SheetColumnType`; does NOT add a `SheetColumnTypeV2`. Test: cell with `"$#,##0.00"` format and value `1234.5` displays `$1,234.50`; cell with `"0.00%"` and value `0.25` displays `25.00%`.

   **Update (session of 2026-08-13, after this row was written):** `SheetCellFormat.swift` already shipped, covering number format (general/number/comma/currency/percent/scientific/date/text), decimals, bold/italic, fill, borders, alignment - most of what this row proposes. Do not build a second type named `CellFormat`; reconcile against `SheetCellFormat` first (rename this proposal's target, or evolve the shipped type). Its `numberFormat` is a categorical enum, not the Excel-format-code string this row describes, so the two are not identical - the string-based format-code parser is still open work if that's the intended shape.

## 8. Out of scope / explicitly punted

- **Full Basic macro compatibility.** The Basic interpreter (`basic/source/comp/*`, `sc/inc/macromgr.hxx`) is a separate language and runtime; embedding it in Tessera Studio would balloon the binary and re-create an entire scripting surface. The agent tool surface (`Tools/SheetTools.swift`) IS the scripting model. Punt.
- **Full chart wizard.** LO's chart wizard lets the user pick from 14 chart types, 6 trendlines, dozens of formatting properties. Tessera should ship a fixed enum of 6 chart types via Swift Charts and treat trendlines as P2.
- **Database connectivity wizard** (`sc/source/ui/dbaccess/`, `connectivity/`). The user can use pandas in the embedded Python interpreter for ad-hoc DB access. The SDBC stack is large and the no-egress doctrine argues against making Tessera Studio a database tool. Punt.
- **Solver wizard UI** (`optsolver.cxx`). The Swift side should call UNO `Solver`; the wizard UI in LO is a 1300-line dialog that duplicates what the agent can express in a single prompt. Punt the wizard, keep the API.
- **Scenarios** (`dpshttab.hxx`, `xmlsceni.cxx`). Branching inputs is rarely used in modern spreadsheets. Punt.
- **Track-changes reviewer UI** (`credlin.cxx`, `XMLChangeTrackingImportHelper.cxx`). The receipt backbone already provides a durable mutation log; building a separate reviewer on top of it can wait for a dedicated `ChangeTracker.swift` at P2.
- **VBA macro import** (`excelvbaproject.cxx`). Excel `.xlsm` files containing VBA can be opened but the macros will be inert in Tessera. Punt; warn on import.
