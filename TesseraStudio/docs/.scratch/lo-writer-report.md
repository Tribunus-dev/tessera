## 1. Scope and methodology

I read the LibreOffice Writer tree on disk at `/Users/user/Developer/GitHub/libreoffice/sw/`, plus its shared dependencies in `editeng/`, `oox/`, and `xmloff/`. I did not clone. The search was bounded by directory listing -> header sampling -> targeted grep. For each subsystem I read the top-of-file of 2-5 representative files (declarations tell you 80% of what a C++ class does), then cross-checked with pattern greps for the canonical term (e.g. `SwSectionData`, `RedlineFlags`, `SwPageDesc`, `SwTOXBase`).

I skipped: the full `unocore/` UNO binding (300+ files, mostly getters/setters that mirror C++ classes), the `view/` rendering pipeline (out of scope for an AST-level product), the `vba/` Word-Basic compatibility layer, and the UI dialog tree under `sw/source/ui/` beyond confirming what the wizard/sidebar entry points exist. I sampled the existing Tessera surface to ground the verdicts: `Productivity/Block.swift` (BlockType, DocumentAST, DocumentPageLayout), `Productivity/DocumentExporter.swift` (HTML->textutil pipeline), `Productivity/Materials/Docs/Doc.swift`, and the full `DocumentProcessing/LibreOffice/` triplet (`LibreOfficeBootstrap.swift`, `EmbeddedPythonBridge.swift`, `tessera_lo_service.py`).

## 3. Block / AST gap analysis

- **No `section` block type.** `BlockType` is a flat list of 16 leaf/structural kinds; LO's `SwSection` (defined in `sw/source/core/docnode/section.cxx`, persisted via `XMLSectionImportContext.cxx`) is the carrier for column changes, index containers, mail-merge envelopes, and protected ranges. This is the single largest hole - without sections you cannot import most real-world DOCX/ODT.
- **No `field` block type.** `DocumentFieldsManager` is responsible for page numbers, references, formulas, mail-merge fields (`sw/source/core/fields/{docufld,expfld,reffld,authfld}.cxx`). Today `DocumentAST` has no field concept at all; the receipt chain cannot model a live page number that re-computes.
- **No `frame` or anchored shape.** `Image` is a block-level picture only. LO's `SwFlyFrame` (`sw/source/core/layout/flylay.cxx`) supports anchored text boxes, OLE objects, and grouped shapes - the gap is structural.
- **Tables are 1-deep.** `BlockType.table` with `children` implies a single level of cells. `sw/source/core/table/swtable.cxx` plus `docnode/ndtbl.cxx` support nested tables, cell merge/span (`rowSpan`/`colSpan`), and repeating headers - `DocumentExporter.swift:235-242` flattens this into `<table><tr><td>` and silently drops spans.
- **No `footnote`/`endnote`.** LO has a dedicated `SwTextFootnote` (`sw/source/core/text/txtftn.cxx`, `core/inc/atrftn.hxx`) and its own numbering counter; `DocumentPageLayout` has no footnote layout, no counter.
- **No `header`/`footer` body.** `DocumentPageLayout.headerBlockID/footerBlockID` exist as UUID pointers (Block.swift:162-164) but nothing populates them; the HTML export in `DocumentExporter.swift:121-194` never reads them. The `BlockType` has no "header" or "footer" container.
- **Partial: lists, comments, track-changes.** `list` has a single `style` attribute; no level/indent hierarchy. `comment`, `trackInsertion`, `trackDeletion` exist as block types but lack a `parentCommentID` (so comment threads are flat), `resolved: Bool`, and `accept`/`reject` lifecycle. LO has a complete `DocumentRedlineManager` (`sw/source/core/inc/DocumentRedlineManager.hxx`) with `AppendRedline`, `SplitRedline`, `DeleteRedline` - we have none of that surface.

## 4. Filter (file format) gap analysis

- **The exporter is a one-way HTML mirror.** `DocumentExporter.swift:90-110` writes self-contained HTML to `/tmp/`, then shells out to `textutil -convert {docx,odt,pdf}`. This breaks on: real tables with rowspan/colspan (HTML->DOCX loses the merge at textutil's level), footnotes/endnotes (no block type to emit), tracked changes (HTML has no `<w:ins>`), fields (HTML can only render a snapshot), multi-column sections (no `cols` block), equations beyond a `$latex$` string, and any anchored drawing.
- **ODT is the worst case.** The header comment at `DocumentExporter.swift:22-24` admits "a native ODF writer is the Phase 2 target." textutil's ODF output from a Word-flavoured HTML is genuinely lossy: paragraph style names are lost, list-level hierarchy collapses, and ODF-specific constructs (text sections, text frames, master pages) cannot be encoded.
- **Importer side is opaque.** `TesseraImporter`/`TesseraExporter` (per the task brief) are a Python subprocess pipeline, not the UNO bridge. We don't know if it round-trips losslessly. DOCX is a ZIP of OPC parts (`oox/source/token/tokens.txt` + `oox/source/export/`); ODT is the same idea with different names. A faithful reader in tesseracore would parse the package, walk `document.xml`/`styles.xml`/`numbering.xml`/`[Content_Types].xml`, and emit blocks - but the cleanest path is to call into the existing UNO bridge and let LO do the parsing.
- **What a native reader would look like.** A pure-Swift ODT/DOCX reader is feasible but big (>=3,000 LoC per format) and overlaps with `xmloff/source/text/` and `oox/source/{export,import}/`. The pragmatic split: UNO bridge for full-fidelity read, a narrow Swift re-implementation only for the "import -> DocumentAST" path on the formats the bridge does not surface well (Markdown, plain text).
- **No filter configuration dialog.** `sw/source/filter/ww8/` has its own `FilterConfig` settings and `sw/source/ui/config/` has filter-options pages; our exporter is fire-and-forget with no "open password-protected DOCX" path, no encryption handling, no password-encryption match.

## 5. Existing LibreOffice bridge surface - what to reuse

The bridge today (`tessera_lo_service.py:363-446`) exposes only four Writer functions: `writer_get_text` (whole-doc string), `writer_get_paragraphs` (per-paragraph style + text), `writer_set_paragraph_style` (assign a named style to paragraph N), `writer_insert_text` (append string). Everything else (`open_document`, `close_document`, `save_document`, `bootstrap_uno`, `dispose`) is format-agnostic. The bridge has a UNO `Desktop`, `ServiceManager`, and `ComponentContext` ready - `tessera_lo_service.py:127-130`.

The right call is to **lean on the bridge for the hard, format-specific problems and keep Swift for the AST + receipt layer**. Specifically:

- **Read paths for ODT/DOCX/RTF/HTML**: drive the bridge. UNO's `loadComponentFromURL` with the right `FilterName` already handles every Writer format correctly - the cost is one process boundary. Tessera should add `writer_to_document_ast(handle) -> DocumentAST` that walks the `XText` cursor (same cursor pattern as `writer_get_paragraphs` at line 386) and emits blocks.
- **Layout-sensitive features** (ToC, page-number fields, cross-references): drive the bridge. LO computes them; we just serialize the resolved text. The field subsystem (`sw/source/core/text/txtfld.cxx`, `porfld.cxx`) is genuinely a thousand-line algorithm.
- **ODF/DOCX export with full fidelity**: drive the bridge's `save_document` with the right `FilterName`; it is already wired (`tessera_lo_service.py:309-360`).
- **Spell-check, autocorrect, grammar, mail-merge wizard, advanced table ops**: do NOT use the bridge. These are LOS-side services that bring a heavy UI/state surface; for the Tessera product we can do better with macOS-native spell APIs and a custom merge coordinator that reuses `Doc.linkedEntityIDs`.
- **The text engine, undo, and receipt chain**: NEVER use the bridge for these. `sw/source/core/undo/UndoCore.cxx` and the receipts infrastructure are LO's own mutation backbone; we have our own (`Productivity/Receipts/ReceiptsCoordinator.swift`, `ReceiptUndoManager.swift`, `Mutation.swift`) and must keep mutations constitutional.

## 6. Proposed tesseracore component design (top 5)

**1. `Productivity/Materials/Docs/SectionStore.swift` + `BlockType.section`** - adds the missing section primitive. Inputs: a `DocumentAST`; outputs: a `[SectionID: Section]` map where `Section` carries `columns: Int`, `columnGap: Double`, `linkedStyleID: UUID?`, `kind: .continuous | .singleColumn | .nextPage | .evenPage | .oddPage | .indexContainer`. The block form `BlockType.section` carries `attributes["sectionRef"]: UUID` and a `children: [UUID]` for the contained blocks. This **evolves** the existing `BlockType` enum and reuses `DocumentPageLayout` (which already exists at `Block.swift:145-196`); it does not create a v2. Test contract: build a DocumentAST with one paragraph, one section (2 columns), one paragraph after; round-trip `jsonData() -> from(jsonData:)`; verify `columnCount == 2` and that the section's children are exactly the two pre-section paragraphs.

**2. `Productivity/Materials/Docs/FootnoteBlock.swift` + `BlockType.footnote` / `.endnote`** - adds the missing note primitives. Inputs: a `Block` with `type: .footnote`, `attributes["number"]: Int`, `attributes["markerStyle"]: "number" | "symbol" | "alpha"`, `content: [InlineRun]` (the note text), `attributes["anchorBlockID"]: UUID` (the block being annotated). Footer/header notes ride the same shape. Talks to `DocumentPageLayout` for `footnoteLineHeight`, `footnoteSeparator: Bool`. Evolves the existing block list. Test contract: place a footnote in a paragraph; assert the rendered `plainText()` does NOT include the footnote text inline (it's pulled out), and that `DocumentExport...` HTML render emits `<sup>N</sup>` in the anchor and the footnote text in a `<footer>` block.

**3. `Productivity/Filters/WriterBridgeFilter.swift`** - UNO-bridge-backed format reader. Inputs: a file URL, an `ImportFormat` (`docx` | `odt` | `rtf` | `html` | `md` | `txt`), a `LibreOfficeBridge` reference. Outputs: a `Doc` (the material) with the body fully populated as `DocumentAST`. Talks to `EmbeddedPythonBridge` to call `bridge_open`, then a new `writer_walk_to_ast(handle)` Python function that iterates the UNO text cursor (parallel to `writer_get_paragraphs` at `tessera_lo_service.py:374-406`) and emits blocks. Evolves the existing `ImportExport` pipeline by replacing the Python subprocess with the in-process UNO call - no `v2` parallel path. Test contract: round-trip a simple DOCX (one heading, one paragraph, one list, one image) through `WriterBridgeFilter.import(URL)` and assert the resulting `Doc.body.rootChildren` count and types match the original within +-0.

**4. `Productivity/Editor/FieldController.swift` + `BlockType.field`** - the field primitive. Inputs: cursor position in the editor, a `FieldKind` (`.pageNumber`, `.crossRef(target: UUID)`, `.formula(expr: String)`, `.date(format: String)`, `.user(name: String)`, `.docProperty(key: String)`). Outputs: a `Block` with `type: .field`, `attributes["kind"]: String`, `attributes["resolvedValue"]: String` (cached for export), `attributes["dirty"]: Bool` (set true when the underlying target moves). Talks to `DocStore` to resolve cross-references and to `ReceiptsCoordinator` so the field update is a receipt-bearing mutation. Test contract: insert a `.pageNumber` field, move the cursor past a `BlockType.divider` (forces a virtual page break), re-render; assert `resolvedValue` updates from "1" to "2" and a `field.update` receipt was emitted.

**5. `Productivity/Editor/RevisionController.swift`** - the redline backbone. Inputs: an `EditorMode` set, a `Revision` (insertion or deletion of a text range) from the editor delta stream. Outputs: a `Block` with `type: .trackInsertion | .trackDeletion` plus `parentRevisionID: UUID?` for the chain. Talks to `ReceiptsCoordinator` (every accept/reject is a receipt) and to `BlockRenderer` (to render in margin/strikethrough). Evolves the existing `trackInsertion`/`trackDeletion` types - adds the missing accept/reject lifecycle, the `author`/`timestamp` chain, and the per-revision ID. Test contract: apply three revisions, accept the first two and reject the third, serialize the AST; assert the resulting `plainText()` matches the pre-revision-1 text, that the receipt log contains exactly three `revision.accept` and one `revision.reject` entries in order.

## 7. Out of scope / explicitly punted

- **Full Basic / VBA macro compatibility.** `sw/source/ui/vba/{vbawordbasic,vbamailmerge,vbadocument}.cxx` is a multi-thousand-line shim that re-implements Word's Basic dialect. Tessera has its own receipt-backed automation layer; we should not import this surface.
- **Full StarMath equation editor.** `starmath/` is its own sibling module; the rendering is a custom TeX-like engine. The `BlockType.equation` with a `latex` string covers the read/round-trip case. A WYSIWYG math editor is a separate product, not a P0-P2 feature.
- **Forms (`sw/source/ui/form/`, `form/source/`).** Form controls tie into the `forms` sibling module and the XForms/UNO control hierarchy. Tessera materials are document-shaped, not form-shaped. Punt to a future "Tessera Forms" track.
- **Mail-merge wizard UI.** `sw/source/ui/dbui/mailmergewizard.cxx` is a 5-page wizard with greeting-page, layout-page, output-type-page, etc. We do not need a wizard; `MailMergeCoordinator` (Section 6 row 2) with a single submit endpoint over `Doc.linkedEntityIDs` is the right shape.
- **Auto-text / glossary blocks.** `sw/source/core/swg/SwXMLTextBlocks{,1}.cxx` implement the auto-complete library. `Doc` already has `tags` and the document search index will subsume most uses; the auto-text UI is a heavy lift with no clear Tessera use case.
- **Section 508 / PDF/UA accessibility tags.** `sw/source/core/text/EnhancedPDFExportHelper.cxx` and the `TaggedPDF` infrastructure are deep work. Tessera already produces PDF via textutil/webkit; native tagged-PDF export is a separate accessibility track.
- **Master documents / sub-documents.** `Doc.linkedEntityIDs` is already a graph edge; the master-document model is a UI for a sub-set of that. Punt until the graph layer has composition operators.
