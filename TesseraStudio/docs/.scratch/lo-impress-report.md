## 1. Scope and methodology

This report is a read-only inventory of LibreOffice's Impress module (`sd/`) and the shared libraries it depends on (`oox/`, `xmloff/`, `avmedia/`, `animations/`, `slideshow/`, `sdext/`, plus the `drawinglayer/`-adjacent `svx/` surface that the slides build on). I read the top of every key file to identify the subsystem, then drilled into the import lists and the canonical public API of each. I did not try to map the entire ~9M LoC tree; instead I sampled representative files per area (5-10 each) and used the directory listings as the structural skeleton. Areas sampled: the core model (`sd/source/core/sdpage.cxx`, `drawdoc.cxx`, `anminfo.cxx`, `TransitionPreset.cxx`, `CustomAnimationEffect.cxx`, `ThemeColorChanger.cxx`, `cusshow.cxx`); the UNO surface (`sd/source/ui/unoidl/unomodel.cxx`, `sddetect.cxx`, `SdUnoOutlineView.cxx`); the filter/export pipeline (`sd/source/filter/pdf/sdpdffilter.cxx`, `eppt/*`, `sd/source/filter/ppt/*`); the OOX/OOXML side (`oox/source/ppt/pptimport.cxx`, `slidetransition.cxx`, `headerfootercontext.cxx`, `layoutfragmenthandler.cxx`, `comments.cxx`, `oox/source/export/*`); the sidebar/animations UI (`sd/source/ui/animations/SlideTransitionPane.cxx`, `CustomAnimationPane.cxx`, `sd/source/ui/sidebar/*` - the master pages container, layout menu, slide background, navigator wrapper); the presenter console (`sd/source/console/PresenterController.cxx` + 70 siblings); the run-time slideshow engine (`slideshow/source/engine/slidebitmap.cxx`, `rehearsetimingsactivity.hxx`, `slideoverlaybutton.cxx`); multimedia (`avmedia/source/macavf/player.mm`, plus the gstreamer/qt6/win siblings); minimizer/`PDF/PPTX compression` (`sdext/source/minimizer/*`); and the auto-layout machinery (`sdpage.cxx:1397 autoLayoutToString`, `:1752 InsertAutoLayoutShape`). On the Tessera side I read `SlideDeck.swift`, `SlideStore.swift`, `SlideReceiptType.swift`, `SlidesGraphConnector.swift`, the head of `SlidesViewModel.swift`, `DocumentExporter.swift`, and the LO bridge trio (`LibreOfficeBootstrap.swift`, `EmbeddedPythonBridge.swift`, `tessera_lo_service.py`) so the "Tessera today" verdicts are grounded in the code, not in my recall. I skipped the `sd/source/ui/inc/` resource files, the `sd/qa/` test corpus except for its directory layout, and the per-language `.hrc` files.

Draw-specific capabilities (layer/snap/connector/measure/3D/text-edit/table/picture) are bundled inside the same `sd/` binary but live mostly in `sd/source/ui/func/fu*.cxx` and `sd/source/core/annotations/`; they are called out in section 2 and section 8 but treated as out-of-scope for the Impress expansion.

## 3. SlideLayout / master slide gap analysis

- The 4-case `SlideLayout` enum (`SlideDeck.swift:10-14`) is a *chrome hint*, not a placeholder set. LO's `AutoLayout` (`sdpage.cxx:1397` `autoLayoutToString`, `xmloff/inc/xmloff/autolayout.hxx`) is a flat enum of ~25 named layouts (TITLE, TITLE_CONTENT, TITLE_2CONTENT, CENTERED_TEXT, VERTICAL_TITLE_VERTICAL_OUTLINE, ...), each declaring a `placeholderSpec: [PresObjKind]` (title, outline, subtitle, object, chart, table, org chart, vertical text, notes). The Tessera evolution is to **replace** the flat enum with a `SlideLayoutSpec` value type that carries `id: String, displayName: String, placeholders: [PlaceholderSlot]`. The 4-case `SlideLayout` becomes the *default* of this type, and the enum's `caseIterable` API is re-exported as a property. This satisfies the no-versioned-implementations rule: the enum evolves, it isn't paralleled.
- Master pages are first-class in LO (`sd/source/ui/sidebar/MasterPageContainer.cxx`, `LayoutMenu.cxx`, `MasterPageDescriptor.cxx`). A master is a *page* (`PageKind::Standard` vs `PageKind::Master`) that holds the background, theme, default placeholder geometry, and the layout list. Add `MasterPage { id, name, placeholders, themeID }` to tesseracore, and `SlideDeck.masterPages: [MasterPage]` + `Slide.layoutMaster: UUID?`. The existing `SlideLayout` becomes a *reference* into `masterPages[i].placeholders` rather than a hard-coded case - that is the actual semantic change.
- A `Slide` already has a `body: DocumentAST` (`SlideDeck.swift:36`). For the master, the natural shape is `MasterPage.body: DocumentAST` (the same primitive, used for the *chrome* of slides bound to the master) plus a `theme` field. The `BlockType` enum is shared (master chrome = same blocks as a slide, with a special `masterOnly: true` flag on root children so the canvas can render chrome distinctly). No new block primitives are required for P0.
- Per-slide *overrides* (LO: each placeholder on a slide can override the master's position, text, and styling) map to a "this block's `position` is local" check inside `enumeratedSlides()` (`SlideDeck.swift:181`). When the master evolution lands, `Slide` grows `localOverrides: [PlaceholderSlot: BlockOverride]` and the canvas composes master + overrides on render. `SlideMeta` (`slideMeta: [String: SlideMeta]` on the deck) is the right home for `localOverrides` because it round-trips without polluting block attributes - exactly the rule the existing comment at `SlideDeck.swift:90-91` already states.
- The existing `SlideReceiptType.setSlideLayout` (`SlideReceiptType.swift:24`) stays. The receipt payload evolves to include `masterPageID: String?` and `placeholderCount: Int`, so undo/restore works without a v2 path.

## 4. Animation / transition / multimedia / presenter console gap analysis

- **Transitions** are the cheapest win. `TransitionPreset` (`sd/source/core/TransitionPreset.cxx`) is just `{ presetId, transition, subtype, direction, fadeColor }` - a flat value type. Add `SlideMeta.transition: TransitionSpec?` (P1; one new struct, one receipt variant). Runtime playback is a SwiftUI `.transition()` modifier + a tween of the next slide; no engine needed at MVP. Punt OpenGL `TransitionerImpl.cxx` to "never" - `slideshow/source/engine/TransitionImpl.cxx` is 1k+ LoC of GPU plumbing we do not need.
- **Animations** are the big delta. LO's `CustomAnimationEffect` (`sd/source/core/CustomAnimationEffect.cxx`, ~3,461 lines) implements the full SMIL-style `XAnimationNode` tree (`ParallelTimeContainer`, `SequenceTimeContainer`, `Animate`, `AnimateMotion`, `AnimateColor`, `AnimateTransform`, `Audio`, `Command`, `IterateContainer`, `Event`). The Tessera P2 surface should NOT mirror the full tree. A flat `[AnimationEffect]` keyed by `targetShapeID` with `effectType in {.entrance, .emphasis, .exit, .motionPath}`, `begin: Duration`, `duration: Duration`, `trigger in {.onClick, .afterPrevious, .withPrevious}` covers 90% of what a deck user expects and round-trips PPTX via the bridge for the other 10%. Store on `Slide.animations: [AnimationEffect]`.
- **Multimedia (audio/video)** lives in `avmedia/source/macavf/` (AVFoundation) and is exactly the right macOS-native primitive to wrap. The bridge already speaks pyuno; tesseracore should expose a `MediaPlayer` Swift wrapper around AVFoundation for play/pause/seek, and a `MediaBlock` (`url, mime, autoplay, loop`) on the slide. P1; P2 for advanced frame-accurate sync with animations.
- **Presenter console** is best implemented by **calling into the existing LO bridge**. The 70-file `sd/source/console/` subsystem is enormous (multi-display, pane factory, theme, accessibility, sprite pane, timer, window manager), and the user can already present any PPTX/ODP via `tessera_lo_service.py` by launching `soffice --show <file>`. Until Tessera grows a native slide show, the right move is: when the user hits "Present", serialize the `SlideDeck` to ODP via bridge, hand the ODP to a `soffice --show` invocation, and have LO run the show (including the presenter console). Native SwiftUI presenter UI is a P2.
- **Recommendation summary:** transitions = tesseracore value type (P1); multimedia = tesseracore SwiftUI + AVFoundation (P1); animations = flat struct list (P2); presenter console = bridge to LO until/unless the user explicitly demands native (P2 or punt).

## 5. File format gap analysis

- `DocumentExporter` (`DocumentExporter.swift:25-50`) exports `DocumentAST` to **DOCX/PDF/ODT only**. There is no native ODP/PPTX export path. For a *slide* deck, ODP/PPTX export is the real export story, and the right architecture is: tessera's `DocumentAST` -> ODP bytes via a thin ODF writer -> `storeToURL("MS PowerPoint 2007 XML", bytes)` via the bridge for PPTX, or `storeToURL("impress8", bytes)` for ODP. The native ODF writer is a small, deterministic serializer (it has to handle `content.xml`, `styles.xml`, `META-INF/manifest.xml`, and the thumbnail). P1 for ODP write; PPTX write is a re-serialize of ODP via LO.
- **Import** is the symmetric story: ODP and PPTX in via the bridge. `tessera_lo_service.py:60` already bootstraps the in-process UNO context and has an `XComponent` registry. Add a `loadDeck(from: URL) -> SlideDeck` that opens the file via `loadComponentFromURL`, walks `XDrawPagesSupplier.getDrawPages()`, and maps each page (slides, notes pages, master pages) to a `SlideDeck`. The mapping is mostly mechanical: `XDrawPage` -> `Slide`, `XShape` (title/body) -> `Block.heading/paragraph`, `XText` -> `InlineRun` array, `XPropertySet` `TransitionType` -> `TransitionSpec`.
- **PDF** is best as bridge-routed. The Tessera PDF path today (`NSPrintOperation` over `NSAttributedString`) is fine for `DocumentAST` (writer-style), but slide rendering is a different problem (16:9, master chrome, image placement). Bridge the ODP render through LO's `sdpdffilter.cxx` and you get the Impress print pipeline for free, including notes/handout export.
- **Image export** (PNG/JPG/SVG) does NOT need the bridge. `SlideRenderer` (Core Graphics) + `UIGraphicsImageRenderer` for a `Slide` AST is a pure-Swift path. P1.
- **PPTX fidelity** is a deep rabbit hole. The `oox/source/ppt/` and `sd/source/filter/eppt/` subtrees are ~60 files of OOXML/Escher mapping, plus `escherex.cxx` for the legacy VML/DML shape records. We should NOT re-implement this; bridge the import and call the LO library a fidelity win.
- **PPT (legacy binary)** is dead for the Impress expansion roadmap. The `sd/source/filter/ppt/pptin.cxx` + `pptatom.cxx` pipeline still exists but is a maintenance burden upstream. If a user gives us a `.ppt`, we route it through LO's importer (which knows the legacy format) and re-export as `.pptx`/`.odp` before tessera sees the AST.

## 6. Existing LibreOffice bridge surface - what to reuse

- `LibreOfficeBootstrap.swift` already discovers the bundle (`bundlePath`/`systemInstallPath`) and exposes `ureBootstrap`, `unoPath`, `pythonHome` (lines 79-100). The bridge is the right place to add new methods, NOT a parallel "v2" service. Extend `EmbeddedPythonBridge` with `openDeck(at: URL) async throws -> SlideDeck` and `exportDeck(_ deck: SlideDeck, to format: DeckExportFormat, at: URL) async throws`.
- `tessera_lo_service.py` already holds an in-process UNO context and an open-document registry (lines 44-57). The right additions are: a `load_deck_as_xdrawpages` (returns the `XDrawPages` enumerable for an Impress document) and a `store_to_format` (writes the active component to a target filter). The existing `bootstrap_uno()` function stays.
- **Call UNO, don't re-implement**, for: the presenter console (a `soffice --show` invocation), ODP/PPTX import (use `loadComponentFromURL`), ODP/PPTX export (use `storeToURL`), and PDF export (use the `sdpdffilter` filter). All four are >10k LoC of upstream code we get to skip.
- **Re-implement in Swift**, for: animation spec authoring (the authoring UI is what we want; runtime playback is a SwiftUI tween), the outline view (we have the AST), notes rendering (we have the `Slide.notes: String` field), and image export (Core Graphics). These are small, SwiftUI-native, and the user-perceptible UX matters more than the underlying engine.
- The bridge is **not** the right home for the presenter console UI. The presenter UI is a SwiftUI surface that talks to the running slideshow; the bridge just spawns and tears down the `soffice` process. Keep `LibreOfficeBootstrap` and the Swift side cleanly split: bridge = transport, SwiftUI = product.

## 7. Proposed tesseracore component design (top 5)

**1. `MasterPageStore.swift` - `TesseraCore/Productivity/Materials/Slides/MasterPageStore.swift`** - Mirrors `SlideStore` but for `MasterPage`. Inputs: `MasterPage { id, name, placeholders: [PlaceholderSlot], themeID, body: DocumentAST }`. Outputs: `createMaster / updateMaster / deleteMaster / listMasters / getMaster`. Talks to the data layer via `graph_entity` rows with `entity_type='document', subtype='slide_master'`. Evolves the existing slide receipt vocabulary by adding `SlideReceiptType.master*` variants (or a parallel `MasterReceiptType` enum if the receipt set diverges). **Test contract:** `MasterPageStore.upsert(masterPage)` then `listMasters()` returns the same master with placeholder count round-tripped and a signed receipt is appended.

**2. `TransitionStore.swift` - `TesseraCore/Productivity/Materials/Slides/TransitionStore.swift`** - Tiny. Wraps `TransitionSpec { presetId, transition, subtype, direction, fadeColor, duration }` and applies it to a `SlideMeta` via `SlideStore.setSlideMeta(...)`. The preset catalog is a static `[TransitionPreset]` literal at first (LO has 30+; the LO `TransitionPreset.cxx:88` reads from `officecfg/Office/UI/Effects` - we can ship a hard-coded JSON catalog for v1). **Test contract:** `TransitionStore.setTransition(slideID, .fade(duration: 0.5))` then `SlideStore.get(id).slideMeta[slideID].transition?.presetId == "fade"` and the receipt is appended.

**3. `SlideDeckRenderer.swift` - `TesseraCore/Productivity/Materials/Slides/SlideDeckRenderer.swift`** - Pure Swift, no UNO. Renders a `Slide` to a `CGImage` (or a `UIView` for in-app). Inputs: `Slide`, master reference, output size. Evolves `Editor/BlockRenderer.swift` to be mode-aware (`EditorMode.document` vs `EditorMode.slideCanvas`); slide canvas is a higher-density layout with master chrome, no inline text-edit affordances. **Test contract:** `SlideDeckRenderer.render(slide).image` is a non-empty `CGImage` of the requested size; rendering is deterministic (same slide -> same image bytes for `seed == nil`).

**4. `LOBridgeDeckIO.swift` - `TesseraCore/DocumentProcessing/LibreOffice/LOBridgeDeckIO.swift`** - Adds two methods on `EmbeddedPythonBridge`: `openDeck(at: URL) async throws -> SlideDeck` and `exportDeck(_:to:at:) async throws`. Internally calls `tessera_lo_service.py` (no Python file changes needed if the existing service already has the UNO context). Mapping is mechanical: `XDrawPage` -> `Slide`, master pages -> `MasterPage`, transitions -> `TransitionSpec`, animations -> `[AnimationEffect]` (flat; we don't try to round-trip the SMIL tree). **Test contract:** `LOBridgeDeckIO.openDeck(testODPURL)` returns a `SlideDeck` whose `slides.count == N` matches the ODP's page count and whose `masterPages` is non-empty for a deck that uses a master.

**5. `DeckExportCoordinator.swift` - `TesseraCore/Productivity/Materials/Slides/DeckExportCoordinator.swift`** - Coordinates the bridge-side export. Decides: for `odp`/`pptx`/`pdf` -> call into the bridge; for `png`/`jpg` -> use `SlideDeckRenderer`. Emits a single `DeckExportResult { url, format, pageCount, warnings: [String] }` so the ViewModel has one observable. Lives next to the existing `DocumentExporter` (which is `DocumentAST`-shaped) and is intentionally slide-deck-shaped; the two coexist because `DocumentAST` and `SlideDeck` are different types. **Test contract:** exporting a 3-slide deck to ODP via the bridge produces a non-empty file; re-importing that file via the bridge returns a deck with 3 slides (round-trip equality on slide count, not byte-level).

## 8. Out of scope / explicitly punted

- **Full animation timeline editor.** A SMIL tree with `ParallelTimeContainer` / `IterateContainer` / motion-path editing is a separate product surface. Punt to P3+ or bridge-driven. We ship the flat `[AnimationEffect]` list at P2; the timeline editor stays out.
- **Full presenter console (dual-display, presenter notes pane, timer, on-stage preview).** Bridge to `soffice --show` for the entire console UX. `sd/source/console/` is 70+ files; we do not re-implement it.
- **Full PPTX import fidelity (Escher shapes, VML, SmartArt, charts, custom geometry, theme parts).** Routed through the LO bridge; we trust `oox/source/ppt/pptimport.cxx` to handle the long tail.
- **Draw-specific capabilities** (layers, snap, alignment helpers, connectors, measure, 3D objects, morph, transform/rotate, custom geometry paths). The user is editing a *deck*, not a *drawing*. Out of scope for the Impress expansion; revisit only if a future "Draw" or "Whiteboard" surface is added.
- **OpenGL transition effects.** `slideshow/source/engine/opengl/` is GPU plumbing. SwiftUI's `.transition()` plus a few Core Animation tweens is enough for the catalog; OpenGL is never.
- **Custom shows as a UX surface.** The data model (`CustomShow` = ordered list of slide IDs) is cheap and we can land it for free; the UI for authoring them is not a P0-P2 concern.
- **PPT (legacy binary) round-trip.** Route through LO's importer as a one-way import only; never write `.ppt` from tessera.
