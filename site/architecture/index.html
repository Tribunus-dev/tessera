Technical depth

The kernel-fidelity loop. The dispatch policy. The memory wall.

The technical depth. The four stages of the pipeline, the dispatch policy across CPU / GPU / ANE, the kernel-fidelity loop in detail, and the memory wall treatment with diagrams. If you have not yet read the concepts, start there for the analogies.

The pipeline

A chain of typed components.

The pipeline is four stages. Each stage takes a typed input, applies a transformation, and emits a typed output. The output is durable. The next stage reads it. Nothing is recomputed from raw artifacts downstream.

Stage 1 · Calibration

per_tensor_calibrate reads the model and a corpus and produces per-tensor statistics: kurtosis, effective rank, outlier density, percentile bounds. The output is a typed component (tensor_stats) keyed by tensor name, model hash, and (in multimodal mode) modality. The calibrator's fitness is offline-Frobenius — the calibrator itself is not the ground truth, but its output is the basis for the GA's search. For multimodal models, the calibrator runs once per modality: text, image, audio, mm projector. The unified output is a single tensor_stats table with the modality stamp on every record.

Stage 2 · AWQ policy search

awq-evolve reads the tensor_stats and runs an island-model GA. The fitness is the Frobenius distance between the original weight and the kernel's dequant output, evaluated through the exact code path the runtime will use. The GA's search is over continuous reconstruction knobs (per-tensor alpha, clip, ternary threshold, outlier fraction), not discrete bit-widths — no prior quantization work searches this space against the kernel directly. The output is a per-tensor policy: alpha, clip, and a verdict (which quant type to use for this tensor). The policy is a typed component (calibration_policy).

Stage 3 · Quantization

llama-quantize --tessera-mode reads the policy, packs each tensor according to its verdict, and writes the GGUF. The policy is embedded in the metadata as a small string (the tensor-family list, not the U/V payloads). The full policy and the GA archive go in a sidecar JSON. SHA-256 in both, for audit. For a multimodal model, the writer absorbs three additional components: vision tower, audio tower, mm projector. The singular-GGUF is the constitutional commitment; the multimodal pipeline does not split the artifact across files.

Stage 4 · Verification

tessera-ab-harness re-runs the kernel dequant on the shipped artifact and compares the output to the original weight. The reported t_l² is the same number the GA optimized against. A green receipt is one where the kernel's dequant matches the calibrator's prediction within tolerance. A red receipt is a bug — either in the calibrator, the GA, or the kernel. The receipt is durable. The artifact is the proof. The proof is the claim.

The kernel-fidelity loop

Measure fitness at the kernel, not the calibrator.

If the run is the artifact, the fitness is the distance between the artifact and the run. The calibrator is a means; the kernel is the ground truth. Tessera's fitness is a Frobenius distance measured after the weight has been dequantized through the exact code path the runtime will use — not a proxy, not an offline estimate, the actual output. The policy is shipped with the artifact. The receipt carries the kernel's hash. A reviewer can re-run the dequant and recover the same number.

Concretely: the GA in awq-evolve builds a candidate policy, applies it to the weight tensor, and feeds the result through the production dequant kernel. The kernel output is compared against the original weight. The Frobenius distance (normalized by max weight magnitude) is the fitness. The GA's search converges on a policy whose dequant output matches the original weight to within the calibrated tolerance. No offline proxy. No separate cost model. The same kernel, the same path, the same answer.

The dispatch policy

Heterogeneous dynamic execution across CPU, GPU, and ANE.

Apple Silicon has three compute engines: the M-series CPU, the GPU, and the Neural Engine. The right engine depends on the operation. Tessera dispatches dynamically at runtime, not statically at compile time. The dispatch policy is a function of the operation type, the input shape, the prompt length, and the current dispatch table state.

OperationEngineWhy
Verifier prefill (long prompts) ANE Matrix prefill is the ANE's strong suit. The verifier prefill is the bottleneck for the first token latency. ANE prefill is async to the GPU via IOSurface hand-off.
Verifier decode (single token) GPU Decode is small-batch matrix work that does not benefit from the ANE's setup overhead. GPU is the right place for it.
Hybrid drafter prefill + decode GPU The drafter is a small model with its own KV cache. GPU keeps the drafter close to the verifier's GPU state for the accept / reject handshake.
Embedding lookup, control flow, sampling CPU Control flow and serial bookkeeping. CPU is the right place. No reason to round-trip through the GPU.
Tokenization, detokenization CPU CPU work. The Apple BPE tokenizer is already on the CPU; Tessera uses it as-is.

The dispatch table is learned, not hard-coded. The embedding_budget tool and the per-tensor activation capture inform which operations land where; the runtime dispatch picks up the table at startup. As the flywheel improves the model, the dispatch table gets sharper — the engine learns the access patterns the model actually exhibits, not the ones the static dispatch policy assumed.

The memory wall

Where inference time actually goes.

The bottleneck in modern local inference is not compute, it is memory bandwidth. The GPU and the ANE can do the math; the question is whether the data is in their caches when they need it. For a 12B model at 4-bit precision, the weights are about 6 GB. For a 12B model at 8-bit, about 12 GB. The compute can finish a token in microseconds; the load takes milliseconds. The math is starving.

Quantization-on-transport shifts the curve

Tessera's answer to the memory wall is quantization-on-transport. Standard quantization is a one-time pre-processing step: the weights are reduced to 4 bits before inference, stored on disk, loaded at startup. The trade-off is fixed at calibration time and applies to the entire inference.

Tessera does quantization as data moves between compute stages. The full-precision weight lives in HBM; the 4-bit representation lives in the GPU's cache; the conversion happens in flight, using the compute that would otherwise be idle during the transfer. The kernel that does the runtime conversion is the same kernel that graded the calibration, so the conversion is kernel-aware and effectively lossless for the model's purposes. The next time the data moves, the conversion happens again, with the access pattern the model actually exhibited.

The effect on the wall: the data-movement bar in the chart above shrinks by roughly the compression ratio of the quantization (4-bit vs 16-bit = 4x reduction in transport bandwidth), and the compute bar grows by the dequant cost (which is small relative to the matmul). The net: faster inference at the same accuracy, with the accuracy verified against the production kernel.

Tessera-T640

The Tile640 encoding, in one section.

Tessera-T640 is the encoding the engine writes. It is a Tile640-aware ternary + outlier representation with AWQ pre-scaling, importance-weighted range selection, and the per-tensor GA. The "T640" means "Tessera, 640-value tile": the encoding carries a balanced ternary core (three values: -1, 0, +1, plus outlier markers), BF16 page scales, INT8 lane-scale codes, and row-sparse F16 residual values for the outliers that the ternary cannot represent.

Sensitive tensors — norms, biases, routers, embeddings — remain exact. They do not pass through the ternary core. The decoder detects them by name in the loader and routes them to the conventional passthrough path. This is the constitutional commitment: protected tensors are never quantized.

The artifact is a single GGUF. The T640 components live in the same file as the conventional tensors. Vanilla llama.cpp readers see standard GGUF; Tessera-aware readers can recover the policy from the metadata and the sidecar.

The calibration corpus

A built-in default, and the path to your own.

The default calibration corpus is shipped baked into the binary. It is approximately 1 MB of synthetic text generated by the Tessera procedural pipeline; the goal is to give a small model enough variety to find a per-tensor policy without a download step. For production calibration, you want your own corpus: a representative sample of the kind of text / images / audio the model will see in deployment.

For multimodal models, the calibration corpus needs three slices: text, image-text pairs, and audio-text pairs. The Tessera CC0 procedural set covers the text slice; for image and audio, the recommended source sets are PixelProse (CC BY 4.0) for image-text and LibriSpeech test-clean (CC BY 4.0) for audio. Both are license-clean for commercial redistribution.
