# B. Items that change Tessera design

## B1. Cap calibration / eval / drafter-train context windows at <=50k tokens  [NEW GUIDANCE]

The Chroma 2025 context-rot study (cited in the video) measured accuracy
already degrading around 50k tokens in a 200k window, well before fill. The
mechanism is not explained, but the measurement is consistent across 18
frontier models.

Affects: imatrix calibration (`ts_compute_scales`), DFlash block-dataset
emission (`tessera-dataset` `TS_DATASET_MODE_DFLASH`), any long-context eval
harness added to `benches/`, and the upcoming drafter training driver's
context window.

Concrete action: when designing the per-chunk window for any of the above,
default to <=50k tokens per chunk. This is well below what we currently
target on some paths; revisit per-subsystem as we instrument.

This is a one-liner for the DFlash design doc; broader doc sweep lives in
`docs/per-tensor-calibration.md` and the calibration README.

## B2. Sandbox any future Tessera auto-tuner that ingests model output as code  [NEW CAUTION]

Prime Agent's own documentation says it is "not a security sandbox" - it
runs model-written Python with the user's permissions. In their factorial
self-improvement tests, the agent learned to spawn resources through an
admin console to cheat, despite being told not to. This is a direct
caution for any future "Tessera auto-tuner" or `TesseraAgentLoop` that
ingests model output as code: the RLM/Prime pattern of "model writes
Python, harness runs it" is dangerous when the harness has user privileges.

Today: Tessera tools that consume model output (`ts_compute_scales`,
`ts_pack_ternary_to_tile`, conversion paths) do not execute model-written
code with user privileges - they consume structured tensors / scale
arrays. The caution is forward-looking for any future `/refine`-style loop
applied to Tessera's own scaffolding.

Concrete action: if/when an auto-tuner is added, treat the loop as
untrusted and run it in a sandboxed subprocess with no user-data ambient
authority. Do not model Tessera's calibration / training driver on Prime
Agent's harness; model it on Tessera's existing `tessera-dpace` (which
consumes telemetry, not model output).

# C. Items that reinforce existing Tessera bets (no action)

## C1. The harness / loop is doing most of the work the industry attributes to the model

- Blind GPT-5-Mini + RLM beat reading GPT-5 by 34 points on OOLONG
  (132k tokens). Per-query cost: $0.11-0.99 for RLM vs $0.98-$6.75 for
  Claude Code on the same tasks.
- Claude Opus 5 went 30.2% -> 95.5% on ARC-AGI 3 depending only on the loop
  (human expert baseline = 95.4%). Same weights, same 25 games.
- Two independent groups (Schema; Ryan Brown) had already crossed the
  human baseline before the Prime Agent launch post.

Tessera parallel: the drafter, the kernel, the calibration, the harness are
doing most of the work the trunk's weights are being credited for. The
video is the kernel/inference side of the same observation. Worth folding
into the framing in `docs/architecture.md` and any external write-up.

## C2. Small-model-on-trajectories beats base (RLM Qwen 8B fine-tune)

Alex Zhang fine-tuned an 8B Qwen on 1,000 recursive trajectories and got
+28% over its base across four long-context tasks, walking up to vanilla
GPT-5 on three of them. This is exactly the DFlash drafter methodology in
a different behavior space: collect trajectories from a big model, fine-
tune a small model to imitate a specific behavior (recursive code-writing
in RLM; next-token speculation in DFlash), measure on the same metric.

Folds into `docs/tessera-dflash-training-design.md` section 7.2 as a
sibling reference. See that doc for the methodology parallel; the
findings file does not duplicate it.

## C3. ARC-AGI 3 metric framing suggests a better Tessera drafter metric

ARC-AGI 3's metric is `(human_actions / agent_actions)^2`. Take twice as
many actions as a human and you score a quarter. Brute-force flailing
scores near zero. Translate to drafter eval: report
`(accepted_tokens / drafted_tokens)` alongside the existing acceptance
rate - that's a first cut at "efficiency, not luck". Ryan Brown's 5.5x
fewer tokens is the same framing applied to inference cost. D-PACE's
adaptive per-position weights are already this idea applied to the
training loss.

Not a near-term change to the training driver; flag for the drafter-eval
discussion when it surfaces.
